

DOCUMENT 5 : Protocole de Sécurité et Gestion de l'État
## 1. OBJECTIF ET RÈGLES DE BASE
Directive pour Antigravity 2.0 : Dans un framework comme Symfony, la sécurité est gérée
en arrière-plan par des middlewares et des composants complexes. Ici, en l'absence totale de
framework et de POO, tu es l'unique responsable de la sécurité.
- Alerte Rouge : Interdiction formelle de créer des classes de type SessionManager,
SecurityHelper ou Auth. Toute la sécurité doit être assurée par des fonctions
PHP pures (ex: auth_login(), generate_token()) regroupées dans des
fichiers utilitaires (ex: /includes/utils/security_functions.php).
- Principe fondamental : Ne faire confiance à aucune donnée entrante (Input) et
échapper toute donnée sortante (Output).
## 2. SÉCURISATION STRICTE DES SESSIONS
- Initialisation unique : La fonction session_start() ne doit être appelée qu'une
seule fois dans toute l'application, tout en haut du fichier /public/index.php,
avant le moindre envoi de contenu au navigateur.
- Durcissement des Cookies (Obligatoire) : Juste avant session_start(), l'agent
devra impérativement configurer les paramètres du cookie de session via
session_set_cookie_params() avec les directives suivantes :
o secure => true (transmission uniquement sur HTTPS).
o httponly => true (protection absolue contre le vol de session via
JavaScript/XSS).
o samesite => 'Strict' (première ligne de défense contre les attaques
## CSRF).
- Prévention de la fixation de session : Lors de toute authentification réussie
(élévation de privilèges), l'agent doit obligatoirement appeler
session_regenerate_id(true) pour renouveler l'identifiant de session et
invalider l'ancien.
- PROTECTION ANTI-CSRF (Cross-Site Request Forgery) MANUELLE
- L'agent devra implémenter un système de jetons de sécurité (tokens) procédural
complet.
- Génération : Création d'une fonction generate_csrf_token(): string qui
utilise bin2hex(random_bytes(32)) et stocke la valeur dans la session
$_SESSION['csrf_token'].
- Injection HTML : L'agent s'assurera que chaque formulaire (Contact, Login Admin,
Modifications Dashboard) inclut un champ caché : <input type="hidden"
name="csrf_token" value="<?= e($_SESSION['csrf_token'])
## ?>">.
- Validation : Création d'une fonction verify_csrf_token(string $token):
bool. La vérification doit impérativement utiliser hash_equals() pour contrer les
attaques temporelles (timing attacks). Si le token est invalide ou absent, la requête
POST/DELETE doit être bloquée net (ex: http_response_code(403);
exit;).

- PRÉVENTION XSS (Cross-Site Scripting) ET FONCTION D'ÉCHAPPEMENT
- La fonction Helper absolue : L'agent devra coder une fonction utilitaire courte
nommée e() dans /includes/utils/security_functions.php.
o Signature attendue : function e(?string $value): string
o Corps exigé : return htmlspecialchars((string) $value,
## ENT_QUOTES | ENT_SUBSTITUTE, 'UTF-8');
- Règle d'affichage universelle : Toute variable PHP insérée dans un fichier de
template HTML (dans le dossier /templates) DOIT obligatoirement passer par
cette fonction e(). Aucune exception n'est tolérée pour l'affichage de données issues
de la base ou des variables utilisateurs.
## 5. VALIDATION ET ASSAINISSEMENT DES ENTRÉES (INPUTS)
- Traitement préventif : Les tableaux superglobaux $_POST et $_GET doivent être
considérés comme hautement corrompus.
- Validation dans les contrôleurs : Au début de chaque fonction contrôleur gérant un
formulaire, l'agent devra utiliser la fonction native filter_input() (ex:
FILTER_VALIDATE_EMAIL) ou des fonctions de validation maison (ex:
validate_contact_data()).
- Rejet anticipé : Si une donnée est invalide, le contrôleur ne doit rien envoyer à la
DAL. Il doit stopper l'exécution, stocker un message d'erreur dans la session (Flash
message procédural) et rediriger l'utilisateur vers la page précédente.
## 6. SÉCURITÉ DE L'AUTHENTIFICATION (ACCÈS ADMIN)
- Hachage des mots de passe : Lors de la configuration du compte administrateur en
base de données, le mot de passe doit être haché en utilisant exclusivement la fonction
native password_hash() avec l'algorithme PASSWORD_DEFAULT (qui gère
BCRYPT ou Argon2).
- Vérification : La tentative de connexion utilisera obligatoirement
password_verify().
- Route Guards (Gardiens de routes procéduraux) : Pour protéger le Dashboard,
l'agent codera une fonction require_admin(). Cette fonction vérifiera si
$_SESSION['is_admin'] est vrai. Si faux, elle doit émettre un header
header("Location: /login") suivi d'un exit; brutal pour empêcher
l'exécution de la suite du script.
