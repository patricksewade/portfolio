

DOCUMENT 4 : Couche d'Accès aux Données (DAL) sans ORM
## 1. OBJECTIF ET PRINCIPES FONDAMENTAUX
Directive pour Antigravity 2.0 : Ce projet exclut totalement l'utilisation d'un ORM (Object-
Relational Mapping) ou d'un Query Builder (pas de Doctrine, pas d'Eloquent). Ton rôle est
d'interagir avec la base de données MySQL de manière strictement procédurale via
l'extension native PDO (PHP Data Objects).
- Exception POO : L'unique tolérance à la Programmation Orientée Objet dans tout le
projet est l'instanciation et l'utilisation de la classe native PDO (ex: $pdo = new
PDO(...) et $stmt->execute()).
- Alerte Rouge : Interdiction formelle de créer des classes modèles personnalisées (ex:
class Project, class User) ou des classes de type "Repository". Toutes les
données extraites de la base doivent être manipulées et retournées sous forme de
tableaux associatifs natifs PHP.
## 2. GESTION DE LA CONNEXION PDO (SINGLETON PROCÉDURAL)
- Fichier cible : /config/db_connection.php (ou équivalent dans le dossier
config/includes).
- Implémentation : L'agent devra créer une fonction dédiée, par exemple
get_db_connection(), qui récupère les identifiants depuis l'environnement.
- Configuration stricte obligatoire (Sécurité et Comportement) : Lors de la création
de l'instance PDO, les attributs suivants doivent impérativement être définis :
- PDO::ATTR_ERRMODE => PDO::ERRMODE_EXCEPTION : Pour que
chaque erreur SQL déclenche une exception catchable.
- PDO::ATTR_DEFAULT_FETCH_MODE => PDO::FETCH_ASSOC : Crucial
pour garantir qu'aucune donnée ne sortira sous forme d'objet anonyme. Seuls
des tableaux PHP doivent transiter.
- PDO::ATTR_EMULATE_PREPARES => false : Sécurité maximale contre
les injections SQL complexes (délégation de la préparation au moteur
MySQL).
## 3. L'INJECTION DE DÉPENDANCE PROCÉDURALE
- Interdiction des variables globales : L'agent a l'interdiction d'utiliser le mot-clé
global pour récupérer la connexion dans les fonctions métier.
- Signature imposée : TOUTE fonction interagissant avec la base de données doit
prendre l'instance PDO en premier paramètre obligatoire.
o Exemple valide : function get_project_by_id(PDO $pdo, int
## $id): ?array
o Exemple invalide : function get_project_by_id(int $id) (avec
instanciation cachée ou globale à l'intérieur).
- Cycle de vie : La fonction get_db_connection() n'est appelée qu'une seule fois
dans le Front-Controller (index.php), puis la variable $pdo est passée en cascade
aux fonctions contrôleurs, puis à la DAL.

## 4. STANDARDISATION DES REQUÊTES (CRUD PROCÉDURAL)
- Fichiers cibles : Regroupement par entité logique (ex:
## /includes/dal/projects_dal.php,
## /includes/dal/messages_dal.php).
- Sécurité absolue (Requêtes Préparées) : Interdiction totale d'utiliser la méthode
$pdo->query() avec des variables PHP concaténées (ex: "... WHERE id =
$id"). L'agent doit systématiquement utiliser $pdo->prepare() suivi de $stmt-
## >execute([...]).
- Typage des retours (strict_types) :
o Pour la récupération d'une ligne unique (ex: find_one) : Le type de retour de
la fonction doit être ?array. L'agent utilisera $stmt->fetch().
o Pour la récupération de multiples lignes (ex: find_all) : Le type de retour
doit être array. L'agent utilisera $stmt->fetchAll().
o Pour les opérations d'écriture (INSERT, UPDATE, DELETE) : Le type de
retour doit être bool (succès de l'opération) ou int (l'ID du dernier élément
inséré via $pdo->lastInsertId()).
## 5. GESTION DES ERREURS ET TRANSACTIONS
- L'agent devra envelopper les requêtes sensibles (surtout les écritures) dans des blocs
try/catch (\PDOException $e).
- En cas d'erreur de base de données, la DAL ne doit jamais afficher l'erreur SQL crue à
l'écran (risque de fuite de structure). Elle doit logger l'erreur via error_log() et
retourner false ou déclencher une exception métier générique que le contrôleur
saura gérer.
- Pour toute opération impliquant plusieurs tables simultanément, l'utilisation
procédurale des transactions est imposée : $pdo->beginTransaction(), $pdo-
>commit(), et $pdo->rollBack().
